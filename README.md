# demogym

Member-retention tooling for a fictional multi-site gym operator, built end to end on synthetic data.

## All data here is synthetic

Every site, member, entry record and piece of equipment in this repository was generated by a script
that is committed alongside it. No real member data, no real operator, no real site. Nothing is sent
to anybody: there is no email, SMS or messaging integration. A model drafts, a person decides, and the
decision is recorded.

## What it does

Every membership gym has access control, so it has a timestamped record of when each member turned up.
Most use it to open a door and for nothing else. Attendance decay is the earliest reliable signal that
a member is about to cancel, and it shows weeks before the cancellation.

demogym scores that signal from entry records alone, then puts a language model on the two jobs that
are actually language jobs.

**Scoring is arithmetic.** Deterministic, auditable and free to run. Decay is measured against each
member's own established pattern rather than a global threshold, because a member who trained four
times a week and has not appeared in nine days is in trouble, while a member who has always come
twice a month is behaving normally. A "no visit in fourteen days" rule flags the second and misses the
first. Every band carries the readings that produced it, so any row can be checked by hand.

**Drafting the intervention.** The model writes the message to a member at risk. It receives computed
facts and never a raw entry row. A reviewer sets tone, length and offer from dropdowns, so no free
text reaches a prompt. The offer is a human choice, because an offer has a price and no model decides
what the business gives away. Approve, Edit and Reject are recorded against the member, and the share
of approvals that needed an edit is the only honest quality measure this project can produce.

**The site briefing.** On request, per site, the model reads computed facts and writes prose for
whoever runs that site: what is happening, who to contact first and why, and any link between
attendance and equipment stated as a hypothesis to check rather than as a finding.

The model does not decide who is at risk, compute a score, a band, a projection or a cost, or choose
who to contact. Everything it is given was derived by code that can be read. That boundary is the
point of the project.

## The screens

| Screen | What is on it |
|---|---|
| Estate | One row per site, ranked by the share of scored members at risk, with a twelve-point trend beside the change against last week |
| At-risk queue | Every banded member, worst first, filterable by site, with the draft controls and the actions on the High band |
| Running this on real data | What this does not do, what it would connect to, the regulatory position, and what the first week of a real engagement contains |

The third screen is part of the deliverable rather than a disclaimer at the end of it.

## How it is built

Next.js 16 and React 19 on Vercel for the pages, Python on Vercel functions for anything that calls
the model or writes to the database, and Neon Postgres for the data. Access is a shared link token in
the first path segment, checked by `proxy.ts` for pages and independently by each Python endpoint.

`planning/` holds the specification, the architecture decisions and one file per slice of work.
`planning/README.md` is the map. `AGENTS.md` governs how work is done here, and `standards/` holds the
language standards it refers to.

## Running it

You need `uv`, Node 24 and a Postgres database. The model features also need an OpenAI key; the
screens and the scoring work without one.

Three environment variables, in `.env` at the root. `.env.example` lists them.

| | |
|---|---|
| `DATABASE_URL` | A Postgres connection string. Neon is what the deployment uses |
| `DEMOGYM_ACCESS_TOKEN` | A long random string. It becomes the first path segment of every URL |
| `OPENAI_API_KEY` | Only needed to draft or to write a briefing |

Install, then create the schema and put an estate in it:

```
uv sync
npm ci

uv run --env-file .env demogym migrate   # creates the eight tables
uv run --env-file .env demogym seed      # generates 6 sites, ~300 members, ~12,000 entries
uv run --env-file .env demogym score     # scores twelve weekly dates
```

`seed` replaces the estate rather than adding to it, and both it and `score` take `--as-of` if you
want a date other than today. `seed` also takes `--seed` for a different draw.

Then run the application. It is two processes in development, because on Vercel each file under
`api/` is its own function and `next dev` serves pages only:

```
npm run dev     # the pages, on :3000
make api        # the Python endpoints, on :5328, proxied from /api
```

Open `http://localhost:3000/<your token>/`. A wrong token gets a page saying the link is not valid.

If you want a different token in development from the one your deployment uses, put it in
`.env.local`. Next.js reads that over `.env`, and `make api` reads both in the same order, so the page
gate and the endpoints agree.

The check gate is `ruff`, `pytest`, `tsc` and `eslint`, in that order, stopping at the first failure:

```
make check
```

It needs no database, no key and no network. Nothing in it verifies that a deployed page renders,
because a typecheck is not a render, so that is a separate command:

```
make smoke                                          # against the deployment
uv run --env-file .env python scripts/smoke.py http://localhost:3000
```

It fetches every screen, checks that each one carries the synthetic-data strip, the cost readout and
content read out of the database, and probes each endpoint with an empty body, which is refused before
any model call. It writes nothing.

## What it deliberately does not do

There is no holdout group, so no claim that the intervention works. There is no contact suppression,
no seasonality, no authentication beyond the shared token, and no observability. Ten datasets an
operator might have were considered and cut, each for a stated reason.

All of it is written down on the running-on-real-data screen, at `/<token>/real-data`, and in
`planning/specification.md`. It is not repeated here, because a third copy is a third thing to keep
true.

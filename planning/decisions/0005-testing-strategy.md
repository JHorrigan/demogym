# 0005 - Test the rules, typecheck the frontend, and record what is not tested

## Context

0001 commits to a single `make check` gate. 0004 puts the reasoning of this project in a Python package, with a thin endpoint wrapping it and a TypeScript application reading stored rows. That leaves three surfaces and they do not deserve equal attention.

The Python package is arithmetic. Given a member and a history, it produces a number or a band, and it decides what a generated day looks like. Arithmetic with edges is what tests are good at, and this is the part of the project with judgement in it. If anything here is wrong, everything downstream is wrong quietly.

The endpoint is a wrapper. It reads a request, calls the package, writes rows, and returns a result. Almost nothing happens in it that does not happen in the package, with two exceptions: it decides whether a request is well formed, and it enforces the rate cap that 0003 calls load-bearing.

The frontend reads rows that already hold their computed values and puts them on a page. There is no rule to get wrong. What can go wrong is a name that does not exist, a shape that does not match, or a page that fails to build, and a compiler catches all three without a test being written.

There is also a question of what a test can honestly establish here. The data is generated by the same rules under test, so asserting that the rules recover a pattern the rules injected proves the code runs, not that it is right. Tests have to assert things that would still be true if the generator were replaced.

## Decision

`make check` runs, in order, `ruff`, `pytest`, the TypeScript compiler, and `eslint`. The first failure stops it. It runs on every push through one GitHub Actions workflow, and it needs no database, no credentials and no network.

| Surface | Covered by | Not covered |
|---|---|---|
| Python rules and generation | pytest, no database | |
| Python SQL layer | | migrations and writes, verified by running them |
| Deployed endpoint | pytest through a test client: input validation, the rate cap, error shape | the deployed function itself |
| Frontend | `tsc` and `eslint` | rendering, behaviour, the deployed page |

Generated data is tested against invariants rather than exact values. No visit before a member joined or after they left, every member attached to a site, every count inside a stated range. Exact values change whenever a rule is tuned, and a test asserting them has to be rewritten each time it does its job, which teaches people to rewrite tests instead of reading them.

Nothing in `make check` touches a real database. The gaps that follow are written down rather than left to be discovered.

## Alternatives considered

**A real Postgres in a container, through Testcontainers.** Real SQL, real migrations, and the one thing that would genuinely verify a migration applies cleanly. Rejected because it puts Docker into a harness that has so far avoided it, and requires it in CI as well. Migrations here are applied by hand, a handful of times, by the person who wrote them, and they fail loudly when they fail. The cost is a standing dependency, and the benefit arrives a few times in the project's life.

**A Neon branch created per CI run.** Real Postgres with no Docker anywhere, which is the better version of the option above. Rejected for now because it needs a Neon API token in CI and branch lifecycle handling, and CI currently needs no secrets at all, which is worth keeping. This is the route if database tests ever earn their place, not the container.

**SQLite standing in for Postgres in tests.** Cheap and fast, no dependency. Rejected outright. The dialect differs, so the migrations under test would not be the migrations that run, and the queries under test would not be the queries that run. A test that passes against a different database is worse than no test, because it reads as coverage.

**Component tests on the frontend, with Vitest and Testing Library.** Rejected because the components render values that are already computed. The assertions would mostly restate the markup, and they would need rewriting every time the markup moved.

**End-to-end tests with Playwright.** The one kind of frontend test that would establish something a compiler cannot, which is that the deployed page loads and the button does what it says. Rejected for now under the rule 0001 sets: added when something has actually broken, not in anticipation. One smoke test against the deployed URL is the cheapest useful version and the first thing to add.

**No tests at all.** Defensible for a prototype nobody depends on, and it would save real time. Rejected because the rules are the deliverable. A project whose point is the reasoning in its arithmetic, with nothing checking that arithmetic, is making a claim it cannot support.

## Consequences

`make check` runs in seconds on a clean machine with no Docker, no network and no credentials. The CI workflow needs no secrets, which is one less thing to leak from a public repository.

Nothing verifies that a migration applies until a person applies it. That is a real gap and it belongs on the list of what this does not do.

Nothing verifies that the deployed frontend renders. A typecheck is not a render, and a page that compiles can still be blank.

0004 records that there is no type checking across the Python and TypeScript boundary. Nothing in this decision closes that. The endpoint's response shape and the frontend's expectation of it are agreed by hand and checked by neither side, and that remains the sharpest edge in the project.

The endpoint tests are the only thing guarding the rate cap. 0003 calls that cap the only barrier between a public control and unbounded writes, so those tests are not optional and they ship in the same slice as the endpoint.

The test suite says nothing about whether the generated data resembles a real gym. It cannot. It checks that the rules hold and the invariants survive, and any claim beyond that would have to be made against real data this project does not have.
